# Варианты удаления зависимых сущностей (`ships_db`)

Документ описывает, **что происходит при удалении строки** в каждой таблице: каскадом, с запретом, с обнулением ссылки или через триггер. Реализация лежит в `init.sql`.

## 0. Принятые решения

- **Скорость `-12` (BALTIC PIONEER) загружается.** Проверки `speed >= 0` нет, все 10 записей попадают в БД.
- **Правило «статус Moored ⇒ скорость ≈ 0» не включаем.** ADVENTURER загружается как есть. Оба случая остаются материалом для тестов (пункт 7 README).
- **Матрица режимов удаления подтверждена** (раздел 3).
- **Журнал удалений (`DeletionLog`) не делаем.** В задании его нет. Вместе с ним убран триггер-журнал.
- **Индексы, партиции и прочая оптимизация в эту лабу не входят.** Они пойдут в следующих лабораторных.

---

## 1. Граф зависимостей

Стрелка `A → B` читается так: «в `B` есть внешний ключ на `A`», то есть `A` — родитель, `B` — зависимая таблица.

```
Country ──┬──> Ship        (flag_country_id, owner_country_id)
          ├──> Voyage      (country_follow_id)
          └──> Port        (country_id)

ShipType ─────> Ship       (ship_type_id)

Ship ─────────> Voyage     (ship_imo) ───────> ShipPosition (voyage_id)
Port ─────────> Voyage     (exit_port_id, destination_port_id)

Company ──────> Supervisor (company_id) ─────> Voyage (supervisor_id)

NavStatus ────> ShipPosition (nav_status_id)
InfoSource ───> ShipPosition (info_source_id)
Sea ──────────> ShipPosition (sea_id)

Sea ──────────> SeaShipCategory <────── ShipCategory
```

Самые длинные цепочки удаления: `Ship → Voyage → ShipPosition` и `Company → Supervisor → Voyage`. Именно на них возможны каскады.

---

## 2. Доступные механизмы

| Механизм | Что делает при удалении родителя | Когда подходит | Риск |
|---|---|---|---|
| **RESTRICT** | Запрещает удаление, пока есть зависимые строки. Проверяется сразу | Справочные данные, на которые ссылаются реальные факты | Приходится сначала вручную чистить зависимые строки |
| **CASCADE** | Удаляет зависимые строки вместе с родителем | Зависимые данные не имеют смысла без родителя | Одно удаление может стереть много строк, в том числе историю |
| **SET NULL** | Обнуляет ссылку в зависимых строках, строки остаются | Ссылка необязательна и строка живёт без неё | Работает только для столбцов, которые могут быть пустыми |
| **Триггер** | Выполняет произвольную логику до или после удаления: запрет по условию, условный каскад | Правила, которые внешний ключ выразить не может | Логику нужно писать и тестировать |

Не используем:
- **NO ACTION.** От RESTRICT он отличается только возможностью отложить проверку, а отложенных ограничений у нас нет. RESTRICT понятнее.
- **SET DEFAULT.** Ему нужны выдуманные «неизвестные» строки в справочниках.

Особенность PostgreSQL: **каскадное удаление запускает триггеры зависимой таблицы.** Если удаляется судно, то удаление его рейсов считается обычным удалением, и триггеры на `Voyage` срабатывают для каждого рейса.

## 3. Итоговая матрица удаления (16 внешних ключей)

Итог: **4 каскада, 2 обнуления, 10 запретов**. В столбце «Пример на данных» результат на тестовых данных из JSON.

| № | Родитель → зависимая (столбец) | Режим | Почему | Пример на данных |
|---|---|---|---|---|
| 1 | `Country` → `Ship.flag_country_id` | RESTRICT | Страна — справочник. Удалить её молча значило бы потерять факт о судне | `USA` удалить нельзя: ею помечен SADIE |
| 2 | `Country` → `Ship.owner_country_id` | RESTRICT | То же | то же |
| 3 | `ShipType` → `Ship.ship_type_id` | RESTRICT | Тип нельзя «забыть», пока есть суда этого типа | `Cruise` удалить нельзя: ADVENTURER и OCEAN TRAVELLER |
| 4 | `Ship` → `Voyage.ship_imo` | **CASCADE** | Рейс не существует без судна. Защита: триггер запрета удаления незавершённого рейса (раздел 4) | Удаление CORAL уберёт 1 рейс и 2 позиции |
| 5 | `Port` → `Voyage.exit_port_id` | RESTRICT | Порт — справочник, рейс без порта выхода теряет смысл | `HAMBURG` удалить нельзя |
| 6 | `Port` → `Voyage.destination_port_id` | RESTRICT | То же | `OSLO` удалить нельзя |
| 7 | `Country` → `Voyage.country_follow_id` | RESTRICT | Справочник | `CAN` удалить нельзя |
| 8 | `Supervisor` → `Voyage.supervisor_id` | **SET NULL** | Рейс важнее оператора. Без оператора рейс остаётся | Удаление Emily Johnson: рейс 7 остаётся, оператор пустой |
| 9 | `Voyage` → `ShipPosition.voyage_id` | **CASCADE** | Позиция без рейса бессмысленна (судно определяется через рейс) | Удаление рейса 4 убирает 2 позиции BALTIC PIONEER |
| 10 | `NavStatus` → `ShipPosition.nav_status_id` | RESTRICT | Статус нельзя восстановить из других данных, поэтому молча терять нельзя | `Moored` удалить нельзя |
| 11 | `InfoSource` → `ShipPosition.info_source_id` | RESTRICT | Столбец обязателен (`NOT NULL`), SET NULL невозможен. Источник нужен для аудита | `EXACTEARTH` удалить нельзя |
| 12 | `Sea` → `ShipPosition.sea_id` | **SET NULL** | Море определяется по координатам, потеря ссылки мало вредит: позиция и её координаты сохраняются | Удаление Barents Sea: у 2 позиций `sea_id` становится пустым |
| 13 | `Country` → `Port.country_id` | RESTRICT | Порт без страны недопустим (`NOT NULL`) | `USA` удалить нельзя: KHATANGA, BETHEL, VALDEZ |
| 14 | `Company` → `Supervisor.company_id` | RESTRICT + триггер очистки операторов | `NOT NULL`, поэтому SET NULL невозможен. Условный каскад выполняет триггер | См. раздел 4 |
| 15 | `Sea` → `SeaShipCategory.sea_id` | **CASCADE** | Строка связи без моря бессмысленна | Удаление Barents Sea убирает 2 связи |
| 16 | `ShipCategory` → `SeaShipCategory.ship_category_id` | **CASCADE** | То же | Удаление `trade` убирает 4 связи |

Почему режимы выбраны так:

- **Каскад там, где зависимая строка — часть родителя** (рейс судна, позиция рейса, строка связи M:N).
- **Обнуление там, где ссылка необязательна, а потеря вредит мало** (оператор, море).
- **Запрет там, где родитель — справочник**, а потеря молча меняла бы смысл фактов: страна, порт, тип, статус, источник, компания.

## 4. Триггеры

Каскады и запреты покрывают структуру. Триггеры нужны там, где решение зависит от **условия**. Их два, у каждого описательное имя.

### 4.1. Запрет удаления незавершённого рейса

| | |
|---|---|
| **Триггер** | `trg_voyage_forbid_delete_active` |
| **Функция** | `fn_voyage_forbid_delete_active()` |
| **Таблица и событие** | `Voyage`, BEFORE DELETE, для каждой строки |
| **Что делает** | Если плановое прибытие (`eta`) ещё не наступило, рейс считается незавершённым, и удаление отклоняется с сообщением, какой рейс мешает |
| **От чего защищает** | От случайного удаления идущего рейса, в том числе **каскадом** при удалении судна: триггер срабатывает на каждом рейсе судна и останавливает всю операцию. Вместе с рейсом пропали бы и его позиции |
| **Как проверить** | Все `eta` в тестовых данных в 2023 году, поэтому они удаляются свободно. Для проверки добавляем рейс с `eta` в будущем и пробуем удалить сам рейс или судно. Ожидаем ошибку |

Ограничение: правило «незавершённый = `eta` в будущем» упрощённое, ведь рейс может завершиться раньше срока. Для лабы достаточно. Чтобы удалить такой рейс принудительно, нужно сначала изменить его `eta`.

### 4.2. Удаление компании вместе с неиспользуемыми операторами

| | |
|---|---|
| **Триггер** | `trg_company_delete_unused_supervisors` |
| **Функция** | `fn_company_delete_unused_supervisors()` |
| **Таблица и событие** | `Company`, BEFORE DELETE, для каждой строки |
| **Что делает** | Удаляет операторов этой компании, **на которых не ссылается ни один рейс**. Если остался оператор, привязанный к рейсу, удаление компании отклоняется с сообщением, кто именно мешает |
| **От чего защищает** | От двух крайностей. Обычный RESTRICT заставил бы вручную чистить операторов. Обычный CASCADE удалил бы операторов, а через SET NULL обнулил бы их в рейсах и потерял связь «кто вёл плавание» |
| **Как проверить** | Компания `ShipVising inc.` не удалится: оператор Sidorov привязан к рейсу 1. Добавленная тестовая компания с неиспользуемым оператором удалится вместе с ним |

Это пример того, что внешний ключ выразить не может: «каскадировать только то, что ничем не занято».

### Не реализуем: мягкое удаление

Вместо физического удаления можно было бы ставить пометку «удалено» (новый столбец) и скрывать такие строки через представление. Минусы: во все запросы нужно добавлять фильтр, `UNIQUE` на `mmsi` и `call_sign` продолжает блокировать новое судно с теми же значениями, и это не демонстрирует то, что просит задание: каскады и триггеры.

## 5. Сценарии проверки на тестовых данных

Исходное состояние после загрузки: **7 судов, 7 рейсов, 10 позиций, 12 связей море–категория**. Это заготовка для пункта 7 README.

| № | Действие | Ожидаемый результат |
|---|---|---|

После каждого сценария данные восстанавливаются откатом транзакции или повторной загрузкой.

## 6. Нюанс

**`TRUNCATE` не запускает построчные триггеры.** Команда `TRUNCATE ship CASCADE` пройдёт мимо запрета удаления незавершённого рейса. Это ограничение самого механизма триггеров. На рабочей базе его закрывают правами: не выдавать `TRUNCATE` обычным ролям.
